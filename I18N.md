# Internationalization in Zymbol

Zymbol answers two different internationalization questions, with two different
mechanisms. Both are built entirely out of the ordinary module system — there is no
annotation, no pragma, no runtime framework.

| Question | Mechanism | Cost at runtime |
|----------|-----------|-----------------|
| **Can a team read and write the *code* in their own language?** | Re-export layers (`#> { alias::fn => name }`) | Zero — resolved to direct references at load time |
| **Can a program show its *text* to a user in their language?** | A dispatcher module holding the active locale as module state | One match arm per call |

They are independent. A program can use either, both, or neither.
[Part 1](#part-1--internationalizing-code) covers the first,
[Part 2](#part-2--internationalizing-runtime-text) the second, and
[Using both](#using-both) shows how they meet in a real program.

> **Every code example in this document has been executed** in both the tree-walker and
> the register VM before publication, and every module file shown passes `zymbol check`
> with no errors or warnings.

# Part 1 — Internationalizing code

## The core insight

Most languages solve i18n for *strings at runtime* (gettext, ICU, resource bundles).
Zymbol also solves a different problem: **i18n for the code itself**. The symbols a
developer reads and types — function names, variable names, constants — can be in any
natural language, because every identifier is a plain Unicode symbol. The module system
provides the bridge between them.

## The three-layer pattern

```
┌─────────────────────┐      ┌──────────────────────────┐      ┌─────────────────────────┐
│   Base Module       │      │   Translation Module      │      │   Consumer Program      │
│   (any language)    │  ◄── │   (pure re-export layer)  │  ◄── │   (own language)        │
│                     │      │   zero logic, zero cost   │      │                         │
│  matematicas/       │      │  matematicas/             │      │  Ελληνική_εφαρμογή.zy   │
│  module.zy          │      │  ελληνικά.zy              │      │                         │
└─────────────────────┘      └──────────────────────────┘      └─────────────────────────┘
```

1. **Base module** — a team writes a library using their own language. It exports a
   public API.
2. **Translation module** — a thin adapter that imports the base module and re-exports
   every symbol under a new name in a different language. Contains no logic whatsoever.
3. **Consumer program** — imports the translation module. Code is written entirely in the
   consumer team's language. They never need to read the base module's language.

## Working example

### Layer 1 — Base module (`matematicas/module.zy`)

Written by a Spanish-speaking team. Exports math operations and constants.

```zymbol
# .matematicas_module {
    #> {
        sumar
        restar
        multiplicar
        dividir
        PI
        E
    }

    PI := 3.14159
    E  := 2.71828

    sumar(a, b)        { <~ a + b }
    restar(a, b)       { <~ a - b }
    multiplicar(a, b)  { <~ a * b }
    dividir(a, b)      { <~ a / b }
}
```

### Layer 2 — Translation module (`matematicas/ελληνικά.zy`)

No logic. It declares what to import and how to re-export it.

```zymbol
# .matematicas_ελληνικά {
    <# ./module => mat

    #> {
        mat::sumar       => προσθέτω
        mat::restar      => αφαιρώ
        mat::multiplicar => πολλαπλασιάζω
        mat::dividir     => διαιρώ
        mat.PI           => ΠΙ
        mat.E            => Ε
    }
}
```

The same file in Hebrew, Korean and Mandarin differs only in the names on the right of
`=>`:

```zymbol
mat::sumar => חיבור          // עִברִית.zy
mat::sumar => 더하다           // 한국인.zy
mat::sumar => 相加            // 中文.zy
```

### Layer 3 — Consumer program (`Ελληνική_εφαρμογή.zy`)

```zymbol
<# ./matematicas/ελληνικά => μαθ

άθροισμα = μαθ::προσθέτω(10, 5)
διαφορά  = μαθ::αφαιρώ(10, 5)
γινόμενο = μαθ::πολλαπλασιάζω(10, 5)
πι       = μαθ.ΠΙ

>> "Άθροισμα: " άθροισμα ¶
>> "Διαφορά: "  διαφορά  ¶
>> "Γινόμενο: " γινόμενο ¶
>> "Πι: "       πι       ¶
```

```
Άθροισμα: 15
Διαφορά: 5
Γινόμενο: 50
Πι: 3.14159
```

Identical output under `zymbol run` and `zymbol run --vm`.

## Re-export syntax

Translation modules rely entirely on the re-export forms available in the `#> {}` block:

| Form | Meaning |
|------|---------|
| `mat::sumar => προσθέτω` | Re-export a **function** from an aliased module under a new name |
| `mat.PI => ΠΙ` | Re-export a **constant** from an aliased module under a new name |
| `mat::sumar` | Re-export a function keeping its name |
| `mat.PI` | Re-export a constant keeping its name |
| `sumar` | Export an own symbol unchanged |
| `sumar => sum` | Export an own symbol under a different public name |

`::` accesses functions from a module alias; `.` accesses constants (non-function
values). Both work in re-export declarations and at the call site.

> **The separator is `=>`, never `<=` or `:`.** Both older forms were valid in earlier
> versions and are rejected by the parser today. See
> [`I18N_DEPRECATED.md`](I18N_DEPRECATED.md) for the document written against the old
> syntax, and `IMPLEMENTATION.md` `[D12]` / `[R03]` for the change record. If you meet
> either of these, that is what happened:
>
> ```
> error: expected '=>' for module alias
> parse error: expected identifier in export item
> ```

## Wrapping the standard library

Zymbol's standard library exposes its functions under fixed names
(`std/random::entero`, `std/io::write`, `std/term::width`). A program written entirely in
one language does not have to call them that way: a translation module is the same three
layers with the standard library as the base.

```zymbol
// std_ελληνικά/τυχαίο.zy
# .std_ελληνικά_τυχαίο {
    #> {
        τυχ::entero   => ακέραιος
        τυχ::rango    => εύρος
        τυχ::peso_f64 => βάρος
    }

    <# std/random => τυχ
}
```

```zymbol
<# ./std_ελληνικά/τυχαίο => τυχαίο

ζάρι = τυχαίο::ακέραιος(1, 6)
>> "Ζάρι: " ζάρι ¶
```

This works for every `std/*` module in both engines. Native stdlib modules are consumed
through the ordinary module system, so re-exporting them needs no special case.

For a full example, see zy-GO's `標準/` directory, which wraps `std/random`, `std/io` and
`std/term` in Japanese so that no call site in the program reads an English identifier.

## Conventions

1. **Base modules** use the host team's natural language for all identifiers.
2. **Translation modules** contain only `<#` imports and a `#> {}` re-export block. No
   logic belongs there.
3. **Module file names** may use Unicode (`ελληνικά.zy`, `한국인.zy`, `盤.zy`). The lexer
   and the filesystem layer support full Unicode paths.
4. **The declared module name must match the file path.** For a file inside a
   subdirectory the name is `<directory>_<file>` with a leading dot:

   ```zymbol
   // matematicas/ελληνικά.zy
   # .matematicas_ελληνικά {     // ✅
   # .ελληνικά {                 // ❌ E001: does not match file name
   ```

   The interpreter will still *run* a mismatched module reached through an import, but
   `zymbol check` and the language server report E001 on it.
5. **Block order inside a module is free.** `<#` before `#>` reads better and is what the
   examples here use, but the parser resolves import aliases used in `#>` re-exports in
   either order.
6. **Version coupling.** Pin the base module version when distributing a translation
   module. A base module API change requires a matching translation module update.

## Team workflow

```
Team A (Spanish)          Team B (Greek adapter)       Team C (Greek consumers)
──────────────────        ─────────────────────        ───────────────────────
Write module.zy           Import module.zy             Import ελληνικά.zy
Publish API in Spanish    Map every symbol to Greek    Write programs in Greek
Maintain business logic   No logic, no tests needed    Never read Spanish code
```

The contract between teams is the **exported symbol list** of the base module. When Team
A adds a function, Team B adds one line. Team C adopts it under their preferred name.

## Design properties

- **Zero runtime cost.** Translation modules resolve at load time to direct references.
  No dispatch table, no string lookup, no penalty against importing the base directly.
- **No special syntax.** i18n is achieved with the ordinary module system (`<#`, `#>`,
  `::`, `.`).
- **Composable.** A translation module can itself be re-exported by a higher-level
  module; a regional-dialect adapter can build on a language adapter.
- **Transparent.** The base module does not need to know about its translators.
- **Language-agnostic literals.** `#1`/`#0` for true/false and symbolic operators for all
  control flow (`?`, `@`, `->`, `<~`) mean there are no English words to break
  foreign-language code.

# Part 2 — Internationalizing runtime text

Part 1 renames *symbols*. It cannot translate *text*, because a string a user reads is
data, not an identifier: `"Play"` and `"Jugar"` are two values, not one value under two
names. That needs a second mechanism.

## The dispatcher pattern

One module owns the active locale and routes every request to the table for that
language. The locale lives in **module state**, which is shared per file path — so every
module importing the dispatcher sees the same selection, and no render function has to
carry a language parameter through the call graph.

```
             ┌────────────────────────┐
             │  textos/despacho.zy    │   holds the active locale
             │  fijar · actual        │   as module state
             │  texto · saludo        │
             └───────────┬────────────┘
                 ┌───────┴────────┐
                 ▼                ▼
      textos/español.zy    textos/english.zy      one table per language,
      (base language)                             same function contract
```

### The locale modules

Every locale implements the **same function contract**. A static key lookup, plus one
composing function for every sentence whose grammar or number formatting differs between
languages:

```zymbol
// textos/español.zy — the base language
# .textos_español {
    #> { texto, saludo }

    texto(clave) {
        <~ ?? clave {
            "idioma.nombre"   => "Español"
            "menú.jugar"      => "Jugar"
            "menú.salir"      => "Salir"
            "aviso.ocupado"   => "ya hay una pieza ahí"
            _                 => clave
        }
    }

    saludo(nombre, partidas) {
        ? partidas == 1 { <~ "Hola {nombre}, llevas 1 partida" }
        <~ "Hola {nombre}, llevas {partidas} partidas"
    }
}
```

```zymbol
// textos/english.zy
# .textos_english {
    #> { texto, saludo }

    texto(clave) {
        <~ ?? clave {
            "idioma.nombre"   => "English"
            "menú.jugar"      => "Play"
            "menú.salir"      => "Quit"
            "aviso.ocupado"   => "there is already a piece there"
            _                 => clave
        }
    }

    saludo(nombre, partidas) {
        ? partidas == 1 { <~ "Hello {nombre}, you have played 1 game" }
        <~ "Hello {nombre}, you have played {partidas} games"
    }
}
```

**Why `saludo` is a function and not a table entry.** Plural agreement, gendered
articles, decimal separators and word order cannot be expressed by a static string table.
Spanish writes `1,5 puntos` where English writes `1.5 points`; Japanese writes `半目`
where English writes `half a point`. Keep `texto()` for fixed labels and give every
composed sentence its own function in the contract.

### The dispatcher

```zymbol
// textos/despacho.zy
# .textos_despacho {
    <# ./español => es
    <# ./english => en

    #> { fijar, actual, idiomas, claves, texto, saludo }

    idioma_actual = "es"

    idiomas() { <~ ["es", "en"] }

    fijar(código) { idioma_actual = código }
    actual() { <~ idioma_actual }

    texto(clave) {
        ?? idioma_actual {
            "en" => { <~ en::texto(clave) }
            _    => { <~ es::texto(clave) }
        }
    }

    saludo(nombre, partidas) {
        ?? idioma_actual {
            "en" => { <~ en::saludo(nombre, partidas) }
            _    => { <~ es::saludo(nombre, partidas) }
        }
    }

    claves() {
        <~ [
            "idioma.nombre",
            "menú.jugar", "menú.salir",
            "aviso.ocupado"
        ]
    }
}
```

The base language is the fallback arm (`_`), so a locale code that does not exist degrades
to the base rather than failing.

### Using it

```zymbol
<# ./textos/despacho => t

t::fijar("es")
>> t::texto("menú.jugar") ¶
>> t::saludo("Óscar", 3) ¶

t::fijar("en")
>> t::texto("menú.jugar") ¶
>> t::saludo("Óscar", 1) ¶
```

```
Jugar
Hola Óscar, llevas 3 partidas
Play
Hello Óscar, you have played 1 game
```

## Keys go in the base language

The keys are **not** neutral ASCII. They are concepts written in the language the program
is written in, each carrying a **domain prefix**:

```
menú.jugar        aviso.ocupado        idioma.nombre
```

A program written in Japanese uses Japanese keys (`区画.アゲハマ`, `報せ.コウ`); one
written in Spanish uses Spanish keys. Asking for `menú.jugar` asks for a *concept*, and
the base-language table is what unfolds that concept into prose. Every other table maps
the same concept into its own words.

**The domain prefix is not decoration — it is what keeps the system verifiable.** The
`_ => clave` fallback means a missing translation renders as its own key, which is how
completeness becomes decidable (next section). That check only works if a key can never
be equal to a correct translation of itself. Without the prefix, the Spanish table
returning `"salir"` for key `"salir"` would be indistinguishable from a missing entry.
With it, the key is `menú.salir` and the translation is `Salir` — they can never collide:

```
clave     : menú.salir
traducción: Salir
¿iguales? #0
```

## The completeness gate

Because a missing key returns the key itself, a test can walk the master catalogue
against every locale and fail on any string that comes back unchanged:

```zymbol
<# ./textos/despacho => t

faltan = 0
@ código : t::idiomas() {
    t::fijar(código)
    nombre = t::texto("idioma.nombre")
    @ clave : t::claves() {
        ? t::texto(clave) == clave {
            >> "  FALTA  [" código "] " clave ¶
            faltan = faltan + 1
        }
    }
    ? faltan == 0 { >> "  [" código "] " nombre "  ok" ¶ }
}
? faltan == 0 { >> "PASS" ¶ } _ { >> "FAIL — " faltan ¶ }
```

```
  [es] Español  ok
  [en] English  ok
PASS
```

Delete one arm from the English table and the gate names it — including in the base
language, which the domain prefix is what makes possible:

```
  [es] Español  ok
  FALTA  [en] menú.salir
FAIL — 1
```

**`claves()` is the contract.** It is the single list every locale must satisfy; adding a
key there and nowhere else makes the gate fail until every language has it. Adding a
language is three edits — write the locale file, import it in the dispatcher, add one arm
to each dispatch function — and the gate tells you immediately what you forgot.

# Using both

The two mechanisms answer questions that a real program asks at the same time. zy-GO —
the game of Go written in Japanese — uses all three of these layers at once:

| Layer | Directory | Mechanism |
|-------|-----------|-----------|
| Standard library in Japanese | `標準/` | Part 1 — re-export (`std/io::write => 書込`) |
| UI text in five languages | `言語/` | Part 2 — dispatcher with Japanese keys |
| Public API in English and Spanish | `api/` | Part 1 — re-export of the engine's own API |

The direction of each layer is worth noticing: `標準/` translates the world **into** the
program's language, `api/` translates the program **out** to other developers' languages,
and `言語/` translates text for the person playing. Three different audiences, two
mechanisms, one module system.

# Verifying your own i18n

```bash
zymbol check path/to/module.zy      # E001 module-name/path mismatch, unused symbols
zymbol run  program.zy              # tree-walker
zymbol run --vm program.zy          # register VM — parity matters for module code
zymbol run  test/completeness.zy    # your own gate, per Part 2
```

Run the VM as well as the tree-walker. Module support in the VM is the part of the
language most likely to diverge, and i18n code is module code almost by definition.
